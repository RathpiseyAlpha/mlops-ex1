    What each part does, and what it leaves to the others.

    Eight boxes, two people. Every box owns one kind of thing: code, jobs, data, models or live requests. Nothing owns two, so each failure has one place to look.

    MLflow remembers every model run and points to the one in use.

    Airflow does the training and makes the decision. MLflow is the ledger and the signpost: it records what each run did, keeps every model it produced, and holds one name, champion, that always points at the version everybody should load.

    Tracking

    Each training run logs its settings, scores, code commit and data snapshot ID. Any result can be traced to its inputs and compared with another run.

    Artifacts

    The trained model file is saved with its run. Scoring, Jupyter or a teammate's laptop can reload exactly that file later.

    Registry

    A candidate becomes a numbered version of iris_classifier. Rejected versions stay, so you can see what was tried and why it lost.

    Champion alias

    Batch scoring loads models:/iris_classifier@champion. Promotion moves the alias forward; rollback moves it back. No code changes.

    Not its job: it does not train models or run schedules (Airflow), hold the labeled data or predictions (ClickHouse), judge whether a candidate is good enough (the promotion policy in Airflow does, then asks MLflow to move the alias), or reload a service that is already running.

    ML developer

    Works in Jupyter. Owns project.py and the model tests. Their commits change how models are trained.

    Data engineer

    Works in Jupyter. Owns ingest.py and the data-contract tests. Their commits change how data arrives.

    Jupyter

    Server B, 10.0.0.11:8888
    Does
    The workbench for people. Edit code, run tests, commit and push, and look at results in ClickHouse and MLflow.
    Keeps
    Notebooks, a local Git checkout, its own Python environment and credentials.
    Talks to
    Git to push, ClickHouse and MLflow to read.
    Not its job
    Production training. Its notebook kernel is not the Airflow worker.
    If it is down
    Nobody can edit or inspect interactively. Scheduled runs carry on.

    Git

    git.example.com, HTTPS 443
    Does
    Single source of truth for code and the history of every change.
    Keeps
    project.py, ingest.py, tests, the DAGs and the dependency lock.
    Talks to
    Jupyter pushes in. CI reads from it. Airflow's deployment agent fetches approved commits.
    Not its job
    Deploying by itself, or holding data and models.
    If it is down
    No new commit can be approved or deployed. The deployed code keeps running.

    CI runner

    ci.example.com, HTTPS 443
    Does
    Tests every proposed commit in a clean environment: unit, integration and dependency checks. Approves one exact commit.
    Keeps
    Test results per commit, and the approval that lets Airflow deploy it.
    Talks to
    Reads Git. Its approval is what the deployment agent trusts.
    Not its job
    Training production models or touching production data.
    If it is down
    New commits wait unapproved. Deployed code and data runs continue.

    Airflow

    Server A, 10.0.0.10:8080
    Does
    The conductor and the runner. Starts jobs on a schedule or an event; runs ingestion, data checks, training, evaluation, the promotion decision, scoring and monitoring.
    Keeps
    DAG definitions, task logs and run history.
    Talks to
    Git to fetch approved code, ClickHouse on 8123, MLflow on 5000.
    Not its job
    Storing datasets or model versions for the long term.
    If it is down
    Nothing is scheduled, trained, scored or monitored. Data, code and model versions stay safe.

    ClickHouse

    Server C, 10.0.0.20:8123
    Does
    The data store. Answers fast analytical queries over labeled snapshots and predictions.
    Keeps
    Immutable labeled snapshots, predictions with the model version that made them, delayed true labels, monitoring summaries.
    Talks to
    Airflow reads and writes rows. Jupyter reads.
    Not its job
    Telling Airflow that new data arrived, or judging whether the data is good.
    If it is down
    Ingestion, training, scoring and monitoring all stop, because each needs data. Code and models are safe.

    MLflow

    Server D, 10.0.0.30:5000
    Does
    Tracks runs, stores model files, registers numbered versions and holds the champion alias.
    Keeps
    Run settings and scores in its database; model files in its artifact store.
    Talks to
    Airflow logs runs, registers versions, moves the alias and loads the champion. Jupyter reads and compares.
    Not its job
    Training, scheduling, holding data, or deciding promotion.
    If it is down
    Training cannot log or register, and scoring cannot find the champion, so batch jobs fail when they load the model. Stored runs and versions return when it is back.

    Prediction API

    Server E, 10.0.0.40:8000
    Does
    The live front door to the champion. Answers POST /predict with the model MLflow currently calls champion, and records every answer.
    Keeps
    The loaded model in memory, and the version number it came from. Nothing else: no data, no history.
    Talks to
    MLflow to find and load the champion, ClickHouse to log requests and true labels, and the app that calls it.
    Not its job
    Training, deciding promotion, or storing predictions itself.
    If it is down
    Apps get errors and no new predictions are logged. Training and batch scoring are unaffected.

    App

    Any client on the network
    Does
    Anything that needs a prediction: a web page, a mobile app, another service. It sends measurements and reads the label and the model version.
    Keeps
    The request_id from each answer, so a later true label can be attached to it.
    Talks to
    Only the Prediction API. It never touches MLflow or ClickHouse.
    Not its job
    Choosing a model version. It always gets whatever is champion.
    If it is down
    Nobody asks for predictions. Everything else keeps running.

    How an app uses the champion model, request by request.

    These are illustrative sketches for this four-server layout. Addresses match the diagram; field names are yours to choose. The app only ever talks to the API, so moving the champion alias in MLflow changes the answers without any app change.

    1. App asks for a prediction

      One HTTPS call with the four measurements. The reply carries the answer, a request ID and the model version that produced it.

      POST https://api.example.com/predict
Content-Type: application/json

{"features": [5.1, 3.5, 1.4, 0.2]}

200 OK
{"request_id": "r-8f3a", "label": "setosa",
 "probabilities": [0.97, 0.02, 0.01],
 "model_version": 4}

    2. API finds the champion

      About once a minute the API asks MLflow which version the alias points to. A moved alias does not reach a running service by itself, so the API reloads when the number changes.

      GET http://10.0.0.30:5000/api/2.0/mlflow/
    registered-models/alias
    ?name=iris_classifier&alias=champion

200 OK
{"model_version": {"name": "iris_classifier",
  "version": "4", "aliases": ["champion"], ...}}

# in the API, when the version changed:
model = mlflow.pyfunc.load_model(
    "models:/iris_classifier@champion")

    3. API records what it answered

      Each answer is saved with the model version, so monitoring can score each version on its own.

      POST http://10.0.0.20:8123/
  ?query=INSERT INTO predictions FORMAT JSONEachRow

{"request_id":"r-8f3a","ts":"2026-11-02 10:15:03",
 "features":[5.1,3.5,1.4,0.2],
 "label":"setosa","model_version":4}

    4. The true label arrives later

      When the real answer is known, the app sends it back. Airflow's monitoring job joins labels to predictions to compute recent quality, and can trigger a rollback.

      POST https://api.example.com/feedback
{"request_id": "r-8f3a", "true_label": "setosa"}

# API inserts into the labels table in ClickHouse

    5. Shortcut: let MLflow serve the model

      For a first version, skip the custom API. MLflow serves the champion itself. You lose request logging and automatic reload, so redeploy when the alias moves.

      mlflow models serve \
  -m "models:/iris_classifier@champion" -p 5001

POST http://10.0.0.40:5001/invocations
{"dataframe_split": {
  "columns": ["sl", "sw", "pl", "pw"],
  "data": [[5.1, 3.5, 1.4, 0.2]]}}

    6. What the app should handle

      The champion can change between two calls, so store model_version with every result. Retry a 503 after a short delay: the API answers it until it has loaded a champion. Never send credentials for MLflow or ClickHouse to the app.

      Each column is one actor. Time runs downward. Hexagons are decisions: a failed test, a failed data check or a weaker model ends the run without changing what is deployed.

      Code stepData stepModel stepApp request stepDecisionStop
      Read the swimlane as a list
        Stage 1: every code change

        Continuous integration tests the program.

        A Git push starts a configured CI workflow. The runner tests the proposed code before it is eligible for deployment.

        Unit tests

        Feature order, preprocessing functions, expected labels and prediction output shape.

        Integration tests

        A small run against a separate test database and tracking store: save a model, reload it, predict.

        Environment checks

        Install pinned dependencies in a clean environment and run a dependency compatibility check.

        Failure: do not approve or deploy that commit. The current Airflow code and model remain in use.

        Stage 2: every eligible data snapshot

        Data tests decide whether training should start.

        Airflow identifies a completed, immutable snapshot and checks its readiness. A table being updated does not prove the data is usable.

        Schema and quality

        Required columns, numeric types, missing values, plausible ranges, unique IDs and target classes.

        Label readiness

        Enough ground-truth labels have arrived. Do not use the current model's guesses as trusted labels.

        Freshness and split isolation

        Detect an already processed snapshot and keep related records out of different splits.

        Failure: record the failed checks and stop training. If no eligible data changed, skip training and continue monitoring.

        Stage 3: every trained candidate

        Model tests decide whether to promote.

        Evaluate the candidate and current champion on the same validation snapshot. Save both the result and the decision reason.

        Quality gates

        Minimum accuracy or F1, gain over the champion, and acceptable performance on important class slices.

        Baseline check

        Also score a trivial model, such as always predicting the majority class or a plain logistic regression. If the candidate cannot beat it, the extra complexity is not earning its place.

        Prediction contract

        Reload the saved artifact; verify feature names, valid labels, probability shape and repeatable predictions.

        Operational limits

        Check inference time, memory and model size against thresholds appropriate to your actual use.

        Failure: keep the candidate for audit, reject promotion and continue using the champion. A rejected model can be a successfully completed training workflow.

        Stage 4: after release, on a schedule

        Monitoring tests the model in use.

        Store predictions with model version, record ID and time. Join later ground-truth labels to compute recent performance.

        Without labels

        Monitor feature distributions, missing values, schema changes, prediction mix and service health. Drift is a warning, not measured accuracy.

        Training and scoring agree

        The same preprocessing must run when training and when scoring. Log the preprocessing together with the model, then compare each scored batch's feature statistics with the training snapshot to catch skew.

        When labels mature

        Compute recent accuracy or F1 on a defined window and compare with your operating thresholds.

        Response policy

        Alert, pause releases, request retraining with ready labels, or roll back to a verified prior version. Do not start unlimited retraining loops.

        Failure: record the incident and apply the configured response; retain a complete audit trail.

        Keep evaluation honest

        Do not turn the final test set into a tuning dashboard.

        Routine candidate selection

        Use training and validation splits or cross-validation. Fit the scaler only on training folds. Use time-aware or group-aware splits when records are related.

        Final release audit

        Reserve a separate final test set for limited release audits. Repeatedly choosing models on the same final test scores causes optimistic estimates.

        The original Iris example used 120 training rows and 30 held-out test rows for one educational run. A continuous system needs an explicit validation and final-audit strategy; this simulation does not pretend to generate new real Iris observations.

        Add these five first

        1. Training and scoring agree. Log the whole preprocessing and model as one scikit-learn Pipeline in MLflow, so scoring cannot apply different transforms.
        2. A baseline in evaluate_candidate. Fail the candidate if it does not beat a majority-class or logistic-regression baseline.

        Outside the rubric: platform basics

        Four things the ML Test Score does not judge.

        • Repeatable runtime environmentsPartly covered

          Dependencies are pinned and tested in a clean environment, but there is no container image or infrastructure as code, so four hand-built servers can drift apart.

        • Secrets and access controlPartly covered

          Credentials stay out of Git and traffic uses HTTPS on a private network. No login or roles are described for MLflow or ClickHouse.

        • Backups and recoveryNot covered

          ClickHouse snapshots and the MLflow database and artifact store are the audit trail, yet no backup or restore test is described.

        • Human sign-off and ownershipNot covered

          Promotion is automatic once the policy passes. Consider an optional approval step for high-risk models, and name an owner for alerts.

        These four are my own judgement, not rubric items.

        Rubric: The ML Test Score. It deliberately leaves out generic software practice such as unit-test coverage and a defined release process, and it was written for supervised models that retrain continuously and serve online. Here, batch scoring makes some tests easier and some less relevant.

        A. Add a code delivery loop

        Git push, CI approval, deploy that commit.

        1. On Jupyter, develop and test project.py. Commit source, tests and dependency specifications.
        2. A Git CI workflow installs dependencies and runs code and integration tests.
        3. Publish the exact tested Git SHA as approved only when checks pass.
        4. A deployment agent on the Airflow execution host fetches the approved SHA over HTTPS. It prepares the environment and updates the DAG and code during a safe deployment window.
        5. Future runs record that SHA. If a deployment check fails, retain the previous working code.

        A push does not deploy by itself. Deploy training and ingestion as separately pinned components, even when they share a Git repository, so an ingestion release does not silently replace the training code. The CI workflow and local deployment agent are additional components to configure. With multiple workers, every execution environment needs the same approved code and dependencies.

        git pushthenCI teststhenapproved SHAthenlocal deployment agent
        B. Add a data delivery loop

        New eligible data can train unchanged code.

        1. Start simply: a daily Airflow schedule checks for a completed, labeled ClickHouse snapshot.
        2. Store the snapshot fingerprint and the code and configuration used to process it. New code can justify a new run on an existing eligible snapshot.
        3. Train only when the data tests and label-readiness checks pass.
        4. Later, let ingestion publish an Airflow Asset event after completing a snapshot.
        5. Set concurrency, deduplication and cooldown policies to prevent overlapping or repeated training.

        A ClickHouse insert does not automatically notify Airflow. Add an ingestion task, API event producer or scheduled readiness check. Drift alone is not a fresh labeled dataset.

        snapshot readythenschedule or Asset eventthenAirflow training DAG
        C. Extend your current DAG

        Make the test gates visible tasks.

        snapshot_readythenvalidate_datathentrain_candidatethenevaluate_candidatethenpromotion_decisionthenscore_batch

        A separate scheduled monitor_champion workflow evaluates new predictions and mature labels. It can request a future retraining run or a rollback according to policy.

        Record for each run

        Git SHA, dependency lock, data snapshot ID, split IDs, random seed, MLflow run ID, model version, metrics and the decision reason.

        Separate failure from rejection

        A crashed task or invalid dataset blocks the workflow. A valid candidate that misses the quality threshold is logged as rejected, while the current champion remains available.

        D. Add a stable model reference

        Consumers load the champion alias.

        After logging a model, register a version in MLflow. Only an approved candidate changes the champion alias. The original hello-world project logged model artifacts but did not add this promotion policy.

        MLflow API sketch, requires a registered version
        from mlflow import MlflowClient
import mlflow.sklearn

client = MlflowClient()
# Execute only after every required gate passes.
client.set_registered_model_alias(
    name="iris_classifier",
    alias="champion",
    version=approved_version,
)

# A batch-scoring consumer resolves this at run start.
model = mlflow.sklearn.load_model(
    "models:/iris_classifier@champion"
)

        Changing an alias does not hot-swap every running process. A batch job resolves it when loading the model; a long-running service needs a reload or deployment mechanism. Retain the prior verified version for rollback.
